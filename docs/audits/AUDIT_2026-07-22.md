# Audit care4success — 2026-07-22

## Résumé exécutif

Premier audit du cycle diagnostic → priorisation → correction → tests → PR mis en place avec les sub-agents Claude Code. Le dépôt est fonctionnel et actif (développement soutenu, derniers commits sur le matching géographique et la refonte du portail public), mais accumule une dette significative sur trois axes : **hygiène du dépôt** (scratch/backup/binaires non gitignorés à la racine, dont un fichier `.env`-like déjà commité dans l'historique), **sécurité applicative** (routes d'écriture non authentifiées, CORS permissif par défaut, secret JWT avec fallback en dur, credentials MySQL en clair dans une dizaine de scripts), et **couverture de tests quasi nulle** côté backend (7536 lignes dans `server/index.js`, 0 test) et côté fonctionnalités critiques récentes (matching géo, inscription). Aucune CI/CD n'est en place. Le reliquat Supabase est confirmé non branché en production (SDK importé uniquement pour des types TS, client jamais instancié côté métier), mais l'historique git contient un secret exploitable qui mérite un traitement immédiat côté tech-lead.

Top 3 risques :
1. Fichier `store.prod.env.fix` **committé** dans l'historique git contenant `JWT_SECRET`/`NEXTAUTH_SECRET` (commit `fcfa00f`) — fuite de secret versionnée.
2. Routes backend d'écriture/statut (`PATCH /api/requests/:id`, `POST /api/requests`, `POST /api/geo/suggest`) accessibles **sans authentification**, sur un total de 143 routes dont seules 65 passent par `authenticateRequest`.
3. Absence quasi totale de tests automatisés sur le backend (0 test serveur) et suite frontend existante déjà **rouge** (`Inscription.test.tsx` : 3 tests en échec sur 5).

## Constats bloquants

### [B1] Secret versionné dans l'historique git (`store.prod.env.fix`)
- Fichiers concernés : `store.prod.env.fix` (racine, tracké, introduit au commit `fcfa00f`)
- Description : Ce fichier est suivi par git (`git ls-files` le liste) et contient des variables `NEXTAUTH_SECRET`, `JWT_SECRET`, ainsi que des URLs/clés d'un projet e-commerce Next.js apparemment sans rapport direct avec care4success (`NEXT_PUBLIC_STRIPE_KEY`, `NEXT_PUBLIC_CLOUDINARY_*`). Qu'il s'agisse d'un legacy issu d'un autre projet ou d'un fichier de travail mal placé, il reste présent dans l'historique git et donc potentiellement exploitable par quiconque clone le dépôt, même s'il était supprimé aujourd'hui (l'historique conserverait le blob).
- Impact : fuite de secrets (JWT signing key, clé Stripe publique/privée selon contenu), utilisable pour forger des tokens ou accéder à des services tiers si les valeurs sont encore valides.
- Effort estimé : S (retrait + rotation des secrets concernés), mais nécessite une décision tech-lead sur la purge d'historique (BFG/filter-repo) qui est une opération plus lourde (L) si elle doit être exécutée.

### [B2] Routes backend sensibles accessibles sans authentification
- Fichiers concernés : `server/index.js:1990` (`POST /api/requests`), `server/index.js:2010` (`PATCH /api/requests/:id`), `server/index.js:2339` (`POST /api/geo/suggest`)
- Description : Sur 143 routes Express définies dans `server/index.js`, seules 65 passent par le middleware `authenticateRequest` (`server/index.js:60`). En particulier, `PATCH /api/requests/:id` permet de modifier le statut (`reçu`, `en traitement`, `assigné`, `clôturé`) de n'importe quelle demande d'inscription sans aucun contrôle d'identité ni d'autorisation, et écrit en plus dans un fichier de debug `/tmp/debug_api.log` via `fs.appendFileSync` avec erreurs avalées silencieusement (`server/index.js:2018`, `2025`).
- Impact : un tiers non authentifié peut altérer le workflow métier (marquer des demandes comme traitées/clôturées), et le chemin `/tmp/debug_api.log` codé en dur suppose un environnement Unix — comportement de debug oublié en production.
- Effort estimé : M (nécessite de revoir la matrice des routes publiques vs protégées, potentiellement risqué si certaines de ces routes sont volontairement publiques pour le formulaire de contact/inscription anonyme — à trancher avec le tech-lead).

### [B3] Credentials MySQL en clair dans une dizaine de scripts à la racine
- Fichiers concernés : `check_db.cjs:4`, `create_admin.js:5-8`, `db_check.cjs:4-7`, `db_cleanup.cjs:4-7`, `db_desc.cjs:4-7`, `deep_clean.js:4-7`, `del_session.cjs:4-7`, `fix_json_columns.mjs:3-6`, `fix_relation.cjs:3`, `resend_teacher_emails.mjs:8-21` (host, user, password MySQL en dur, hors variables d'environnement)
- Description : Ces scripts (tous **non trackés** par git à ce jour — `git status` les liste en `??`) contiennent des identifiants de connexion MySQL en clair (host `127.0.0.1`, utilisateur `care4success`, mot de passe explicite). Certains fichiers voisins (`check_ethan.mjs`, `fix_db.mjs`) utilisent correctement `process.env.DB_HOST`/`DB_PASSWORD`, montrant une incohérence de pratique entre scripts.
- Impact : ces fichiers sont actuellement hors du dépôt versionné mais présents sur le poste/serveur de développement ; un `git add -A`/`git add .` accidentel (déjà un risque réel vu le volume de fichiers untracked à la racine, cf. [M1]) les committerait avec les secrets. Risque de fuite si le poste ou une sauvegarde est partagé.
- Effort estimé : S (déplacer vers variables d'environnement + confirmer qu'ils sont bien ignorés par `.gitignore` ou supprimés).

- Description : Tous ces fichiers sont actuellement `??` (untracked) selon `git status`, donc pas encore dans l'historique — mais ils polluent la racine du dépôt et plusieurs contiennent des secrets (cf. ### [M2] Couverture de tests quasi inexistante côté backend et suite frontend existante en échec
- Fichiers concernés : `server/index.js` (7536 lignes, 143 routes, 0 fichier de test associé), `src/pages/Inscription.test.tsx`, `src/pages/auth/Login.test.tsx`, `src/components/GeoSelector.tsx`
- Description : Seuls deux fichiers de test existent dans tout le dépôt (`src/pages/auth/Login.test.tsx` et `src/pages/Inscription.test.tsx`). Aucun test ne couvre `server/index.js`, ni les fonctionnalités récentes de matching géographique (`feat(geo)`, `feat(matching)` — derniers commits). L'exécution de `vitest run` montre en outre que la suite existante est déjà rouge : `Inscription.test.tsx` échoue à 3 reprises sur 5 tests, notamment `GeoSelector` qui lève `No QueryClient set, use QueryClientProvider to set one` faute de wrapper TanStack Query dans le test — signe que le test n'a pas été mis à jour après l'intégration du composant géographique.
- Impact : aucune garde-fou automatisé sur l'authentification, les routes de matching/inscription ou la logique métier serveur ; la suite frontend actuelle ne peut pas servir de baseline fiable en CI tant qu'elle reste rouge.
- Effort estimé : M à L selon le périmètre visé (relève de `unit-test-engineer`/`integration-test-engineer`, pas de ce rapport).

### [M3] Absence de CI/CD
- Fichiers concernés : `.github/` (contient uniquement `PULL_REQUEST_TEMPLATE.md`, aucun dossier `workflows/`)
- Description : Aucun workflow GitHub Actions n'existe pour exécuter `npm run lint`, `npm run test:ui`, `npm audit` ou un build de vérification à chaque PR, alors que le dépôt vient précisément de se doter d'un cycle de sub-agents structuré (diagnostician → tech-lead → dev → tests → doc) qui suppose normalement un filet de sécurité automatisé.
- Impact : rien n'empêche aujourd'hui de fusionner du code qui casse le lint, les tests ou introduit une régression ; la qualité repose entièrement sur la discipline manuelle.
- Effort estimé : M.

### [M4] Dépendances avec vulnérabilités connues, dont plusieurs critiques sur des libs directes
- Fichiers concernés : `package.json` (dépendances directes `axios`, `concurrently`, `jspdf`, `multer`, `nodemailer`, `lovable-tagger`)
- Description : `npm audit` rapporte 34 vulnérabilités (4 critiques, 17 hautes, 11 modérées, 2 basses) sur 1109 dépendances totales. Parmi les paquets **directs** touchés : `jspdf` (critique — injection HTML/XSS via fenêtre, CVSS 9.6, utilisé pour générer des PDF de factures/bulletins côté client), `concurrently` (critique, via `shell-quote`, utilisé uniquement en dev pour `npm run dev:full`), `axios` (haute sévérité, multiples CVE SSRF/pollution de prototype, utilisé côté client pour les appels API), `multer` (haute — DoS sur upload de fichiers, utilisé pour les pièces jointes/messages), `nodemailer` (haute — injection SMTP/SSRF, utilisé pour les emails transactionnels).
- Impact : `jspdf` et `multer` sont branchés sur des flux utilisateur (upload de fichiers, génération de documents), donc l'exposition n'est pas que théorique. Le rapport ne préjuge pas de l'exploitabilité réelle sans revue du contexte d'usage.
- Effort estimé : M (mise à jour de versions à valider avec le tech-lead, hors périmètre de correction directe de ce rapport — pas de `npm audit fix` exécuté).

### [M5] Absence de validation d'entrée et de durcissement HTTP côté backend
- Fichiers concernés : `server/index.js:1804-1805` (`app.use(cors({ origin: corsOrigin }))`, `app.use(express.json())`), `server/index.js:25` (définition de `corsOrigin`), `server/index.js:37-38` (`JWT_SECRET`)
- Description : `corsOrigin` vaut `true` (reflète n'importe quelle origine) si la variable d'environnement `CLIENT_ORIGIN` n'est pas définie. `express.json()` est monté sans limite de taille de body. Aucune librairie de validation d'entrée (type Zod, utilisé côté frontend) n'est utilisée côté serveur — la validation se fait au cas par cas via des `if (!champ)` manuels épars. `JWT_SECRET` utilise un fallback en dur `"care4success_dev_secret"` si la variable d'environnement est absente (avec un simple `console.warn`, sans blocage au démarrage) — ce repo ne contient pas le `.env` de production donc l'audit ne peut pas confirmer si la variable est bien positionnée sur le serveur PM2, mais le pattern de fallback silencieux est en soi une mauvaise pratique.
- Impact : surface d'attaque CORS élargie par défaut, absence de limite de taille de payload (risque DoS), absence de validation systématique (risque d'injection de données malformées), dépendance à la discipline opérationnelle pour éviter l'usage du secret JWT par défaut.
- Effort estimé : M.

### [M6] `npm run lint` : 401 problèmes (6 erreurs, 395 avertissements)
- Fichiers concernés : voir annexe — erreurs concentrées dans `src/pages/common/VirtualClassroom.tsx` (blocs vides `no-empty` lignes 292, 325 ; non-null assertion dangereuse sur optional chaining lignes 573, 590), `src/pages/teacher/Homework.tsx:59` (`no-empty`), `src/pages/teacher/Schedule.tsx:327` (`no-useless-escape`)
- Description : Le linter tourne et se termine en erreur (exit code 1) à cause de 6 erreurs bloquantes ESLint, en plus de 395 avertissements majoritairement `@typescript-eslint/no-explicit-any` (très nombreux, ex. `src/api/backoffice.ts` en compte près de 50) et `no-unused-vars`. Les erreurs `no-empty` masquent potentiellement des branches de gestion d'erreur volontairement vidées (ex. écriture de logs en `try {} catch {}`).
- Impact : `npm run lint` ne peut pas servir de gate CI en l'état sans échouer systématiquement ; le volume de `any` traduit un typage TypeScript affaibli sur les couches API/back-office.
- Effort estimé : S pour les 6 erreurs bloquantes, L pour un nettoyage significatif des `any`.

## Constats mineurs

### [m1] Reliquat Supabase confirmé non branché en production, mais toujours importé
- Fichiers concernés : `src/integrations/supabase/client.ts` (client instancié conditionnellement via `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`), `src/api/backoffice.ts`, `src/components/dashboard/TeacherApplicationsBoard.tsx`, `src/components/dashboard/TeacherRatingsBoard.tsx`, `src/components/TeacherFeedbackForm.tsx`, plusieurs pages `admin`/`advisor`/`parent` qui importent uniquement des **types** depuis `@/integrations/supabase/types`
- Description : Confirmation de l'hypothèse de contexte — `getSupabaseClient()` (défini dans `client.ts`) n'est appelé nulle part ailleurs dans `src/` ; toutes les autres références à `@supabase/supabase-js`/`@/integrations/supabase/*` dans le code métier ne portent que sur des imports de type (`import type {...} from "@/integrations/supabase/types"`), pas d'appel réseau réel. Le SDK Supabase reste néanmoins une dépendance directe de `package.json` et un client complet est instancié en mémoire si les variables d'env sont présentes, sans être utilisé.
- Impact : dette de nettoyage plutôt que risque actif ; à surveiller si un nouveau développeur réutilise `getSupabaseClient()` par erreur en pensant qu'il s'agit du canal de données réel.
- Effort estimé : S (à confirmer avec le tech-lead avant suppression : ce constat touche potentiellement une réorganisation du typage backoffice).

Le script npm `test:edge-functions` (`cd supabase/edge_function && deno task test`) n'a donc rien à exécuter de significatif. Dernier commit touchant `supabase/` : `08af9f8` (bien antérieur aux commits récents de matching/geo).
